# 6. Packages

## Import

### Theory

- **Core Concepts**: The `import` statement tells the compiler which fully-qualified type names (classes, interfaces, enums, annotations) a source file wants to refer to by their simple name. It is purely a compile-time convenience — it does not load classes, does not affect the generated bytecode, and does not create any runtime dependency by itself. Java supports single-type imports (`import java.util.List;`) and on-demand (wildcard) imports (`import java.util.*;`), which bring every public top-level type in a package into scope.
- **Internal Working**: The compiler resolves simple names by consulting the import list, the current package, and `java.lang` (implicitly imported); it rewrites simple names to fully-qualified names purely inside the `.class` file's constant pool references — no `Import` bytecode instruction exists.
- **When to Use It**: Use single-type imports for clarity and to avoid ambiguity; use wildcard imports sparingly (some teams disallow them) when a file uses many types from one package, such as `javax.swing.*` in UI code.
- **Advantages**: Improves readability by allowing short names, avoids repetitive fully-qualified references, enables IDEs to auto-manage dependencies.
- **Limitations**: Wildcard imports can cause name clashes that only surface when a new type is added to an imported package later; imports are not transitive (importing a class doesn't import its nested classes or its package's other types); they only work for types, not for static members (that requires `import static`).

### Internal Working

- **Step-by-Step Explanation**: 1) Parser scans `import` declarations at the top of the compilation unit. 2) For every simple type name used in the file, `javac` searches: (a) types declared in the same file, (b) single-type imports, (c) types in the current package, (d) on-demand imports, (e) `java.lang.*`. 3) If more than one on-demand import supplies a type with the same simple name and it is actually used, compilation fails with an ambiguity error. 4) The resolved fully-qualified name is emitted into the `Constant_Class_info` entries of the class file's constant pool — the compiled `.class` file has no trace of which import statement was used.
- **Memory Layout**: Not directly applicable — imports are a source-level/compile-time construct only; they have no heap, stack, or metaspace footprint themselves. The *classes* they refer to are loaded into metaspace/heap only when actually used at runtime, driven by the class loader, not by the import statement.
- **Diagrams**:

```
source file (MyClass.java)
  import java.util.List;      -- single-type import
  import java.time.*;         -- on-demand import
        |
        v  (javac name resolution)
  simple name "List"   -> java.util.List   (constant pool: Ljava/util/List;)
  simple name "LocalDate" -> java.time.LocalDate (found via wildcard)
```

- **JVM Behaviour**: The JVM never sees import statements — it only sees fully-qualified binary names embedded in the constant pool of the compiled class. Class loading for referenced types is deferred until first active use (lazy loading), following the standard loading → linking → initialization sequence, completely decoupled from where/how the source imported the type.

**Basic**
1. What is the difference between a single-type import and an on-demand (wildcard) import?

3. Why is `java.lang.*` never explicitly imported in most Java files?

**Intermediate**

**Advanced**
6. How does `javac` resolve simple names when a type is imported but a nested/inner class in the current file has the same simple name?
7. Why don't imports work for static members, and what specific mechanism (`import static`) solves this?

**Scenario-based**
8. Your team enforces a "no wildcard imports" checkstyle rule. What concrete compile-time or maintenance risk does this rule guard against?

### Detailed Answers

1. A single-type import (`import java.util.List;`) brings exactly one named type into scope, making the import list explicit and IDE-refactor-friendly. An on-demand import (`import java.util.*;`) makes every public top-level type of that package available by simple name, but does **not** recursively import sub-packages (`java.util.concurrent` is a distinct package and needs its own import).
2. No. Imports are resolved entirely by the compiler; the resulting bytecode references fully-qualified class names in the constant pool regardless of which import form was used. There is zero runtime performance difference — the only costs are compile-time name lookup and, arguably, a marginal risk of future ambiguity errors.
3. `java.lang` (containing `Object`, `String`, `Integer`, `Exception`, etc.) is implicitly imported into every compilation unit by the Java Language Specification, so writing `import java.lang.*;` is legal but redundant.
4. If both simple names are actually referenced in the file, `javac` raises a "reference to X is ambiguous" compile error and forces the developer to disambiguate with a fully-qualified name or a single-type import. If only one of the colliding classes is actually used in the file, there's no error — ambiguity is only checked against *actual usage*, not just the presence of the import.
5. Yes — if the current file also declares (or inherits) a type with the same simple name as the imported one (e.g., a nested class `Point` shadowing `java.awt.Point`), the compiler prefers the locally visible name, and you must use the fully-qualified name (`java.awt.Point`) to reach the imported type.
6. Name resolution follows a strict priority: types visible in the enclosing scope (including inherited members and nested classes of the current class) take precedence over single-type imports, which in turn take precedence over on-demand imports. This mirrors general Java shadowing rules — the "closest" declaration wins.
7. Regular `import` only maps simple type names to fully-qualified type names; it has no mechanism for referring to a *member* (a `static` field or method) without qualifying it by its declaring class. `import static java.lang.Math.*;` (or a single static import) extends the resolution table to also map bare member names like `PI` or `max(...)` directly to `Math.PI` / `Math.max`.
8. Wildcard imports create a "silent breakage" risk: if a new class is later added to one of the wildcard-imported packages with the same simple name as a class from another wildcard import (or a class already used elsewhere), previously-compiling code can suddenly fail to compile, or worse, silently resolve to the wrong type if only one import is wildcarded and the other is a stale unrelated dependency. Explicit single-type imports make every dependency visible in a diff and eliminate this class of surprise.

### Code Examples

```java
// Single-type imports: explicit, refactor-safe, preferred in production code
import java.util.List;
import java.util.ArrayList;
import java.time.LocalDate;

public class OrderService {
    public List<String> summarize(List<LocalDate> orderDates) {
        List<String> summaries = new ArrayList<>();
        for (LocalDate date : orderDates) {
            summaries.add("Order placed on " + date);
        }
        return summaries;
    }
}
```

```java

import java.util.*;   // java.util.List
import java.awt.*;    // java.awt.List (an AWT component!) - both packages define "List"

public class ImportAmbiguityDemo {
    // This line fails to compile: "reference to List is ambiguous"
    // List names = new ArrayList<>();

    // Disambiguating with a fully-qualified name resolves it:
    java.util.List<String> names = new java.util.ArrayList<>();
}
```

## Static Import

### Theory

- **Core Concepts**: `import static` (introduced in Java 5) extends the import mechanism to `static` members — fields and methods — of a class or interface, allowing them to be referenced by simple name without the enclosing class qualifier. For example, `import static java.lang.Math.*;` lets code write `sqrt(x)` instead of `Math.sqrt(x)`.
- **Internal Working**: Exactly like regular imports, this is a compile-time-only name-resolution aid; the compiler rewrites bare member references to fully-qualified `ClassName.member` invocations/field accesses in the generated bytecode (`invokestatic` / `getstatic` instructions reference the owning class directly).
- **When to Use It**: Idiomatic for DSL-style code, unit test assertion libraries (`import static org.junit.jupiter.api.Assertions.*;`), mathematical code using `Math.*`, or enum constants used repeatedly within a single class.
- **Advantages**: Reduces visual noise for heavily-used utility methods/constants, makes test code read like natural assertions (`assertEquals(expected, actual)` instead of `Assertions.assertEquals(...)`).
- **Limitations**: Overuse harms readability by hiding the origin of a symbol, increases risk of naming collisions with local variables/methods, and static-imported wildcard members are just as prone to ambiguity issues as regular wildcard imports.

### Internal Working

- **Step-by-Step Explanation**: 1) `javac` parses `import static pkg.ClassName.member;` (single-static) or `import static pkg.ClassName.*;` (on-demand static). 2) When resolving a bare identifier or method call that isn't a local variable/field/method of the current class, the compiler checks the static-import table for a matching static field or method in the referenced class. 3) On match, the compiler emits the same bytecode as if the member had been explicitly qualified — `getstatic`/`putstatic` for fields, `invokestatic` for methods.
- **Memory Layout**: Not directly applicable — no additional runtime memory structures are created; the static members still live exactly once in the method area/metaspace of the class that declares them, regardless of how many files statically import them.
- **Diagrams**:

```
import static java.lang.Math.sqrt;
import static java.lang.Math.PI;

double c = sqrt(PI * r * r);
         |         |
         v         v
invokestatic Math.sqrt   getstatic Math.PI
```

- **JVM Behaviour**: Because static imports resolve to ordinary `invokestatic`/`getstatic` bytecode, they carry zero runtime overhead versus explicit qualification and participate normally in JIT inlining decisions (e.g., `Math.sqrt` can be intrinsified by the JIT compiler using hardware instructions regardless of the import style used to invoke it).

### Interview Questions

**Basic**
1. What problem does `import static` solve that a regular `import` cannot?
2. Give a common real-world example where static imports improve readability.

**Intermediate**
3. What is the difference in bytecode, if any, between calling `Math.sqrt(x)` and calling `sqrt(x)` after a static import?
4. What are the readability risks of overusing static imports?

**Advanced**
5. How does the compiler disambiguate a bare method call when both a static-imported method and an instance method with the same name/signature are in scope?

**Scenario-based**
6. You're reviewing a PR that adds `import static java.util.Collections.*;` to a class that also has a local variable named `emptyList`. What issue might arise, and how would you resolve it?

### Detailed Answers

1. A regular `import` only maps simple *type* names to fully-qualified type names; it cannot bring a `static` field or method into unqualified scope. `import static` adds a second resolution table specifically for static members, enabling code like `PI` instead of `Math.PI`.
2. Testing frameworks are the canonical example: `import static org.junit.jupiter.api.Assertions.*;` lets test methods read as `assertEquals(expected, actual)` and `assertThrows(...)` rather than being prefixed with `Assertions.` everywhere, closely mirroring natural-language assertions.
3. There is no difference whatsoever — both compile to an identical `invokestatic java/lang/Math.sqrt:(D)D` instruction. Static import is purely a source-level convenience; the constant pool and instruction stream are indistinguishable from the explicitly qualified form.
4. Because the qualifying class name is omitted, a reader (or an IDE without full semantic highlighting) cannot immediately tell where a bare identifier like `MAX_VALUE` or a method like `of(...)` comes from, especially with multiple wildcard static imports in the same file; it also increases the chance that a locally-declared variable or method shadows, or is shadowed by, an imported static member.
5. Members declared in or inherited by the current class always take precedence over statically-imported members — the compiler only falls back to the static-import table if no applicable member is found in the current class's own scope (fields, methods, inherited members). This mirrors the general rule that lexically closer declarations shadow imported ones.
6. The local variable `emptyList` merely shadows the *name* within its scope; since `Collections.emptyList()` is a *method call* (`emptyList()`) not a bare identifier, there's no actual naming conflict — Java distinguishes variables from method invocations syntactically. However, if the wildcard import brought in a field or constant with the exact same name as a local variable, the local variable would simply take precedence within its scope, which could silently hide the intended imported symbol; the fix is to use a single specific static import or qualify the reference explicitly (`Collections.emptyList()`) for clarity.

### Code Examples

```java
import static java.lang.Math.PI;
import static java.lang.Math.pow;

public class CircleMetrics {
    // Reads naturally thanks to static imports, avoiding repeated "Math." prefixes
    public static double area(double radius) {
        return PI * pow(radius, 2);
    }
}
```

```java
// Typical JUnit 5 usage pattern relying on static imports for readable assertions
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

class CircleMetricsTest {
    void areaIsComputedCorrectly() {
        assertEquals(78.5398, CircleMetrics.area(5.0), 0.001);
        assertThrows(IllegalArgumentException.class, () -> CircleMetrics.area(-1));
    }
}
```

## Package Visibility

### Theory

- **Core Concepts**: "Package visibility" (also called package-private or default access) is the access level applied when a class, field, method, or constructor is declared **without** any explicit access modifier (`public`, `protected`, `private`). A package-private member is visible only to other types declared in the *same package*, regardless of inheritance relationships across packages.
- **Internal Working**: The JVM enforces this at both compile time (`javac` rejects out-of-package access) and, critically, at class-loading/linking time via bytecode verification — the `access_flags` of a class or member simply lack the `ACC_PUBLIC`/`ACC_PROTECTED`/`ACC_PRIVATE` bits, and the JVM's field/method resolution algorithm checks the caller's package against the declaring class's package.
- **When to Use It**: Ideal for internal helper classes/methods that support a package's public API but shouldn't leak as part of it — a classic technique for enforcing encapsulation at the package level before JPMS existed, and still useful within a single module today.
- **Advantages**: Enables package-level encapsulation, letting cooperating classes in one package share implementation details without exposing them publicly; supports the common pattern of package-private constructors combined with public static factory methods.
- **Limitations**: Because Java packages are "open" by default (historically, unrelated code could declare a class in the same package name — a "split package" scenario), package-private is a weaker security boundary than JPMS module encapsulation; it's also easy to forget and accidentally leave a member with default access.

### Internal Working

- **Step-by-Step Explanation**: 1) At compile time, `javac` checks that the referencing code's package matches the declaring type's package when no explicit modifier is present; a mismatch is a compile error. 2) At class-file level, the member's `access_flags` in the `field_info`/`method_info` structure has none of `ACC_PUBLIC`, `ACC_PRIVATE`, `ACC_PROTECTED` set. 3) At link time (specifically during verification and on first use via `getfield`/`invokevirtual`/etc.), the JVM's access control algorithm (JVMS section 5.4.4) compares the run-time package of the accessing class (defining class loader + package name) against the run-time package of the declaring class; access is granted only if they match.
- **Memory Layout**: Not directly applicable in terms of heap/stack, but relevant at the metaspace level — the JVM stores each loaded class's package name as part of its identity (a class is uniquely identified by binary name **and** defining class loader), which is exactly what enables the classic "classloader-based sandboxing" trick of putting untrusted code in the same package name but loaded by a different class loader, defeating naive package-private assumptions.
- **Diagrams**:

```
package com.acme.billing;

class InvoiceCalculator {      // package-private class
    double compute(...) { ... }   // package-private method
}

package com.acme.billing;      -- same package: CAN access InvoiceCalculator
package com.acme.reporting;    -- different package: CANNOT access it, even in the same module
```

- **JVM Behaviour**: Access checks are performed by the verifier and by the `invoke*`/`getfield`/`putfield` resolution logic at link time; an illegal cross-package access to a package-private member throws `IllegalAccessError` at runtime if it somehow slipped past compile-time checking (e.g., via separately compiled/mismatched class files), demonstrating that visibility is a runtime-enforced JVM concern, not merely a `javac` courtesy.

### Interview Questions

**Basic**
1. What is package-private (default) access, and how do you declare a member with it?
2. How is package-private access different from `protected`?

**Intermediate**
3. If two classes declare the same package name (`com.acme.util`) but are loaded by two different class loaders, can they access each other's package-private members?
4. Why might a library author deliberately choose package-private over `private` for a helper class?

**Advanced**
5. How does the JVM enforce package-private access at the bytecode level, independent of `javac`'s compile-time checks?
6. How does the Java Platform Module System (JPMS) change or strengthen the guarantees of package-private access?

**Scenario-based**
7. You maintain a public API in package `com.acme.api` and want to share internal utility code with `com.acme.api.internal` without exposing it publicly. Package-private alone won't work across those two package names — what are your options?

### Detailed Answers

1. Package-private access is the access level applied automatically when no `public`, `protected`, or `private` modifier is written on a top-level class, field, method, or constructor. A member with default access is visible only to code in classes that share the exact same package name.
2. `protected` grants access to the same package **plus** subclasses in other packages (via inheritance, with the restriction that the access must occur through a reference of the subclass type or its subtype). Package-private grants access strictly to same-package code and does **not** extend to subclasses in different packages at all.
3. No. The JVM's notion of a "runtime package" combines both the package name **and** the defining class loader. Two classes with an identical package name loaded by different class loaders are considered to be in different runtime packages, and cross-package-private access between them is denied — this is precisely the mechanism that prevents malicious code from injecting a class into `java.lang` to reach package-private JDK internals.
4. Package-private lets a small cluster of cooperating classes within the same package share an implementation-detail helper class (e.g., a builder, validator, or cache) without making it part of the package's public API, while still allowing multiple classes in that package to reuse it — something `private` (visible only within a single top-level class) cannot do.
5. Each loaded class's constant pool and `access_flags` record its members' visibility; when bytecode performs `getfield`, `putfield`, `invokevirtual`, `invokespecial`, or `invokestatic` against a member, the JVM's linkage/resolution algorithm (JVMS section 5.4.4) checks whether the member has default (no explicit) access and, if so, verifies that the calling class and the resolved class share the same runtime package (name + class loader); a violation throws `IllegalAccessError`, independent of anything `javac` already checked.
6. JPMS adds a coarser, module-level encapsulation layer on top of package visibility: by default, no package is exported from a module, meaning even `public` types in a non-exported package are inaccessible to other modules via strong encapsulation (enforced by the module system at both compile time and runtime) — package-private still governs same-package access as before, but JPMS additionally lets you hide entire packages (all their public members included) from consumers outside the module unless explicitly `exports`-ed.
7. Options include: (a) restructure so the internal helper lives in the same package as its only consumers, sacrificing some package organization; (b) use JPMS and keep `com.acme.api.internal` un-exported (or `exports ... to` a restricted set of modules) while making the helper `public` within that internal package, relying on module boundaries instead of package-private; (c) use a documented "internal, not part of public API" convention with `public` visibility, accepting weaker enforcement; JPMS (option b) is the strongest and most idiomatic modern solution.

### Code Examples

```java
package com.acme.billing;

// Package-private class: only usable by other classes inside com.acme.billing
class TaxCalculator {
    // Package-private method: implementation detail, not part of any public API
    double calculate(double amount, double rate) {
        return amount * rate;
    }
}

public class Invoice {
    private final TaxCalculator taxCalculator = new TaxCalculator();

    public double total(double amount, double taxRate) {
        // Same package -> allowed to use the package-private class and method
        return amount + taxCalculator.calculate(amount, taxRate);
    }
}
```

```java

        // TaxCalculator calc = new TaxCalculator(); // package-private, inaccessible here
        System.out.println("Report for invoice total: " + invoice.total(100.0, 0.08));
    }
}
```

## JPMS Module Declarations (`module-info.java`) *(new, cross-reference)*

### Theory

- **Core Concepts**: The Java Platform Module System (JPMS, JSR 376, introduced in Java 9) lets a JAR declare itself as a *module* via a `module-info.java` file at its root. A module declaration names the module (`module com.acme.billing { ... }`) and lists directives: `requires` (dependencies on other modules), `exports` (packages visible to other modules), `opens` (packages visible for deep reflection, e.g., by frameworks), `uses`/`provides` (service loader integration), and `requires transitive` (re-exporting a dependency to consumers).
- **Internal Working**: `module-info.java` compiles to a special `module-info.class` containing a `Module` attribute; at runtime the JVM builds a *module graph* from these descriptors, and the module system enforces both readability (`requires`) and accessibility (`exports`/`opens`) independently of classpath-style visibility.
- **When to Use It**: For libraries and applications that want strong encapsulation of internal packages, explicit dependency declarations, and reliable configuration (fail-fast on missing dependencies) rather than relying on the classpath's flat, unstructured JAR list.
- **Advantages**: Strong encapsulation (non-exported packages are truly inaccessible, even via reflection, unless `opens`-ed), reliable configuration (missing/duplicate module errors surface at startup, not as obscure `NoClassDefFoundError`s later), smaller custom runtimes via `jlink`.
- **Limitations**: Migrating large legacy codebases to modules is often costly (split packages, automatic modules, illegal reflective access from frameworks like older Hibernate/Spring versions); many real-world applications still run on the classpath (unnamed module) rather than the module path.

### Internal Working

- **Step-by-Step Explanation**: 1) `javac` compiles `module-info.java` into `module-info.class`, embedding a `Module` attribute describing requires/exports/opens/uses/provides. 2) At launch, if the application runs from the module path, the JVM's module system resolves the full module graph starting from the root module(s), computing readability edges (`requires`) transitively, and fails fast with `FindException`/`ResolutionException` if a required module is missing or if there are duplicate modules on the path. 3) At class-loading time, in addition to the classic package-visibility check, the JVM verifies that the accessing module *reads* the target module and that the target package is *exported* (or *opened*, for reflective access) to the accessing module; otherwise it throws `IllegalAccessError` or, for reflection, `InaccessibleObjectException`.
- **Memory Layout**: Not directly applicable to heap/stack, but each module's classes are still loaded into metaspace exactly as with the classpath; the module graph itself (a small in-memory structure of `Module`/`Configuration`/`ResolvedModule` objects) is built once at JVM bootstrap and held for the life of the process.
- **Diagrams**:

```
module com.acme.billing {
    requires java.sql;                     // read edge to java.sql module
    requires transitive com.acme.core;     // re-exported dependency
    exports com.acme.billing.api;          // public API package, readable by other modules
    opens com.acme.billing.model to com.fasterxml.jackson.databind; // deep reflection for JSON
}

      com.acme.billing  --requires-->  java.sql
             |
             +--exports--> com.acme.billing.api   (visible to any module that `requires com.acme.billing`)
             +--opens---->  com.acme.billing.model (reflective access limited to Jackson)
```

- **JVM Behaviour**: Module resolution happens during JVM bootstrap (before `main` executes) when running from the module path; class loading afterward is delegated to three built-in loaders (bootstrap, platform, application) each associated with sets of modules, and every `invoke*`/`getfield`/reflective `setAccessible(true)` call is subject to both classic access-modifier checks and the additional module-readability/`exports`/`opens` checks — a `public` class in a non-exported package is loadable within its own module but throws `IllegalAccessError` when accessed reflectively or directly from another module without an `opens`/`exports` directive.

### Interview Questions

**Basic**
1. What is a `module-info.java` file, and where does it live in a project?
2. What is the difference between `requires` and `exports` in a module declaration?

**Intermediate**
3. What does `opens` do, and how is it different from `exports`?
4. What happens if module A `requires` module B, but module B is missing from the module path at launch?

**Advanced**
5. What is `requires transitive`, and when should you use it?
6. What is an "automatic module," and how does JPMS handle a plain JAR (without `module-info.class`) placed on the module path?

**Scenario-based**
7. A Spring-based application fails at startup with `InaccessibleObjectException` when Spring tries to reflectively access a private field in one of your model classes, after you migrated the app to JPMS modules. What is happening, and how do you fix it?

### Detailed Answers

1. `module-info.java` is a special source file placed at the root of a module's source tree (e.g., `src/main/java/module-info.java` in a typical Maven/Gradle layout) that declares the module's name and its dependencies/exports via directives inside a `module ModuleName { ... }` block. It compiles to `module-info.class`, which the JVM reads to build the module graph.
2. `requires` declares a *dependency*: "this module needs to read that other module to compile/run against its exported types." `exports` declares *visibility outward*: "this module makes the given package's public types accessible to any module that requires this one." A module can `require` things without exporting anything, and can `export` packages that have no `requires` at all (if they only use `java.lang`, for instance).
3. `opens` grants **reflective** access (via the `java.lang.reflect` and `java.lang.invoke` APIs, including deep reflection into private members) to a package at runtime, without making it accessible for ordinary compile-time `import`/reference use. `exports` grants **both** compile-time and runtime accessibility to public types but does *not* by itself permit reflective access to non-public members. Frameworks like Jackson, Hibernate, or Spring that use reflection to instantiate/inspect classes typically require the containing package to be `opens`-ed to them (or opened unconditionally with `opens pkg;`).
4. The module system performs resolution before the application starts; a missing required module causes the JVM to fail immediately at launch with a `FindException` (module not found) wrapped in a startup error, rather than failing later at first use with a `NoClassDefFoundError` as would happen on the classpath — this "fail fast, fail loud" behavior is one of JPMS's key reliability benefits.
5. `requires transitive` means that any module which `requires` your module automatically also gets a readability edge to the transitively-required module, without needing to declare it explicitly. It's used when your module's public API exposes types from the dependency (e.g., a method returning `java.sql.Connection` means your module should `requires transitive java.sql;` so consumers can use the returned type without a separate explicit `requires`).
6. An automatic module is created when a plain (non-modularized) JAR is placed on the module path instead of the classpath. The JVM derives its module name either from the `Automatic-Module-Name` entry in the JAR's manifest (preferred, stable) or by algorithmically deriving one from the JAR's filename (fragile, changes if the filename changes). Automatic modules implicitly `export` all of their packages and `require` all other modules (including other automatic modules and the unnamed module), acting as a bridge/compatibility mechanism during incremental modularization.
7. This happens because the model class's package was not `opens`-ed to Spring's module (or `opens`-ed unconditionally), so the module system blocks the reflective `setAccessible(true)` call Spring needs to read/write private fields. The fix is to add `opens com.acme.model to spring.core;` (or the actual module names Spring components live in) — or, if broad reflective access is genuinely needed and encapsulation is not a priority for that package, `opens com.acme.model;` to open it to all modules; alternatively, remaining on the classpath (unnamed module) sidesteps the restriction entirely, since the unnamed module has no module encapsulation.

### Code Examples

```java
// module-info.java at the root of the module's source set
module com.acme.billing {
    requires java.sql;
    requires transitive com.acme.core;      // re-exported: consumers of billing also read core

    exports com.acme.billing.api;           // public API, usable by any module that requires this one
    exports com.acme.billing.dto to com.acme.reporting; // qualified export: only reporting can see it

    opens com.acme.billing.model to com.fasterxml.jackson.databind; // allow Jackson's reflection

    uses com.acme.billing.spi.PaymentGateway;              // service consumer
    provides com.acme.billing.spi.PaymentGateway
        with com.acme.billing.internal.StripeGateway;       // service provider
}
```

```java
// A module that consumes com.acme.billing's exported API
```
